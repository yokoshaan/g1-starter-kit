# ここから先の開発

このキットで動かせるのは「遠隔操作」「教示と再生」「点群の確認」までです。ここから何に進めるか、道筋と入口を書いておきます。

---

## いま手元にあるもの

| | 何に使えるか |
|---|---|
| 腕の関節角の時系列（`data.json`） | 模倣学習の学習データ、軌道解析 |
| 点群 + IMU の bag | SLAM、地図作成、障害物検出の入力 |
| テレオペの経路（DDS） | 独自コントローラを書くときの参考実装 |

**bag と記録さえ取ってあれば、ロボットが無い場所でも開発を進められます。** ここが実機開発の要点です。まずデータを取る手段を確保したことに意味があります。

---

## 1. 教示再生の限界を超える（模倣学習）

再生をやってみると、**物の位置を少しずらすだけで失敗する**ことがすぐ分かります。記録は「関節角の時系列」でしかなく、「赤いカップを掴む」という意図は入っていないためです。

そこを埋めるのが模倣学習です。

**必要になるもの**

- **視覚**: 現状の記録には画像が入っていません（頭部カメラを使う場合はロボット内蔵 PC 側の画像サービスが必要）。手首や外部に USB カメラを付けて記録に足すのが現実的な第一歩です
- **データ量**: 同じタスクを配置を変えて数十〜数百エピソード。テレオペで淡々と集める作業になります
- **学習側**: ACT / Diffusion Policy などが入口。[LeRobot](https://github.com/huggingface/lerobot) はデータ形式と学習・評価が揃っていて始めやすいです

**このキットからの繋ぎ方**

`data.json` は `states`（実測）と `actions`（目標）を 30 Hz で持っています。LeRobot のデータセット形式へ変換するスクリプトを書くのが最初の作業になります。`tools/replay_arm.py` の `load_episode()` が読み方の参考になります。

学習したポリシーを実機で動かす部分は、`tools/replay_arm.py` の送信処理（`_send` / `_prepare_header`）がそのまま使えます。記録軌道の代わりにポリシーの出力を入れるだけです。

---

## 2. 点群から地図を作る（SLAM）

`--decay` で点を残すと、ロボットが動いた瞬間にズレます。これが SLAM が必要な理由です。自己位置を推定しながら点を重ねる必要があります。

**入口**

- **FAST-LIO2**: LiDAR + IMU の慣性オドメトリ。Mid-360 での実績が多い。ROS 2 対応のポートを使います
- 入力形式に注意: 実装によって `PointCloud2` ではなく Livox **CustomMsg** を要求します。その場合は `./scripts/lidar_view.sh --custommsg` で bag を録ってください
- **上下逆さま搭載について**: FAST-LIO は LiDAR 内蔵 IMU を使い、点群と IMU はセンサ座標系内で整合しています。**ドライバ側で点群だけ回転させないでください**（IMU と不整合になります）。地図が天地逆に出たら、出力の PCD を後処理で回すか表示側で回します

**ゴール**: bag → 3D 地図（PCD）。ここまで来ると、地図の上で経路を考える段階に進めます。

---

## 3. 地図の上で経路を作る（ナビゲーション）

3D 地図を高さでスライスして 2D の占有格子に落とせば、**Nav2** の経路計画がそのまま使えます。

**進め方**

1. PCD を高さ帯（例 0.2〜1.5m）でスライスして xy に投影し、占有格子（PGM + YAML）にする
2. `nav2_map_server` で配信し、`nav2_planner` に経路を計算させる
3. 出てきた `nav_msgs/Path` を歩行 API に繋ぐ

**ここが本番の難所です。** Nav2 が出すのは車輪型を前提にした速度指令（`cmd_vel`）で、二足歩行の G1 に直接は渡せません。歩行 API との間を埋める層が必要になります。まずは「地図を作って経路が引けるところまで」を目標にして、歩行との接続は分けて考えるのが現実的です。

学習の順番としては、**`nav2_costmap_2d` の膨張（inflation）の考え方**から入るのがおすすめです。「ロボットの体の大きさを考慮すると通れない隙間がある」ことが視覚的に分かり、経路計画が何をしているのか掴めます。

## 4. テレオペ自体を拡張する

| やりたいこと | 手がかり |
|---|---|
| ハンド（Inspire / Dex3）を動かす | `xr_teleoperate` の `--ee` 引数。`teleop/robot_control/robot_hand_*.py` |
| 手追従（ハンドトラッキング）にする | `./scripts/teleop.sh --input-mode=hand` |
| 頭部カメラの映像を一人称で見る | ロボット内蔵 PC 側の画像サービス（`teleimager`）が必要 |
| 歩行と腕を同時に動かす | `--motion` を付けるとモーションコントローラと併用になり、`rt/arm_sdk` 経由になる（[04-record-replay.md](04-record-replay.md) 参照） |
| 独自の操作デバイスを使う | `teleop/televuer` が XR の入力を抽象化している。ここに別の入力源を足す |

## 5. 仕組みを理解するために読むと良いところ

このキットのコードは「なぜそうしているか」をコメントに書いてあります。動かしたあとに読むと理解が早いです。

| ファイル | 読むと分かること |
|---|---|
| `tools/replay_arm.py` | DDS で関節を動かす最小の形。`mode_machine` や制御権 weight、ゲインの意味 |
| `tools/lidar_probe.py` | LiDAR がネットワーク上でどう名乗るか。UDP のパケット構造 |
| `scripts/lib.sh` | conda と ROS を分ける理由、DDS ドメインの分離 |
| `setup/apply_patches.py` | 上流のどこに何の問題があるか |
| `~/xr_teleoperate/teleop/robot_control/robot_arm.py` | 逆運動学の解を関節指令に変換する部分。速度制限やゲインの実装 |

**とくに `robot_arm.py` の `__init__`** は、「全関節を現在角度でロックしてから腕だけ動かす」という実機制御の基本形が読めるので、一度目を通す価値があります。

## 最後に

実機開発でいちばん時間を取られるのは、アルゴリズムではなく **「繋がらない」「動かない」の切り分け** です。このキットが潰してある落とし穴は、どれも実際に数時間かかったものです。

同じ種類の詰まりに遭ったら、[06-troubleshooting.md](06-troubleshooting.md) の最後にある切り分けの順番（リンク → 到達 → データ → 待ち受け）を思い出してください。**「プロセスは生きているのにデータが流れていない」** 状態を見落とさないことが、いちばん効きます。
